# 插件中心原理与界面

[返回 Wiki](README.md)

## 谁负责什么

| 插件作者 | MT 宿主 |
| --- | --- |
| 提示词、识别策略、调用顺序、异常处理 | 模型客户端、凭据、限流、取消 |
| 声明配置、动作和结果列 | 渲染表单、浏览文件、展示结果 |
| 提交识别建议与草稿 | 目录范围、方案、TMDB 类型和季集核验 |
| 返回文本结果和日志 | 用户确认、封存检查、真实整理与任务管理 |

插件不是一段嵌入 MT 的网页。它是 `plugin.json` 加预打包 `dist/index.js`，在独立 Goja 工作进程中运行，使用同步 JSON SDK。没有 Node、任意网络、文件系统、环境变量、命令或宿主服务对象。

## UI 如何生成

`config` 定义设置页的长期配置；`actions` 定义运行页的动作和一次性输入；`columns` 定义普通结果表。`files` 字段由 MT 文件选择器处理，`profile` 字段生成授权方案选择器。插件作者无需写 React、CSS，也不能提供前端 JS。

调用 `organize.prepare` 后，MT 将草稿放入固定整理预览，支持搜索、筛选、分页、修正和确认；这些行为不是插件返回 HTML 实现的。用户最终确认来自登录后的 MT 界面，工作进程没有 submit 方法，不能自行声称已确认。

插件中心的卡片、安装流程、四页签和状态标签由 MT 统一维护。自定义插件使用通用图标和清单信息；官方目录使用 MT 静态配置补充介绍和分类。官方标识核对安装来源，不信任作者自报的名称。首版没有市场服务器、评分或下载量。

## 数据如何流动

1. 管理员检查公开仓库或内置副本，固定内容并授权目录、方案与能力。
2. MT 扫描文件，向工作进程发送不透明引用、文件名、授权目录内相对路径等白名单信息。
3. 插件通过 `ai`、`tmdb` 等方法调用宿主；每次重新检查启停、安装修订和授权。
4. MT 保存核验草稿，界面展示结果，用户修正后产生新修订。
5. 用户确认具体草稿修订，MT 重新检查文件和方案，逐文件提交原手动整理队列。

模型、文件名、插件输出均不可信。无法通过 SDK 读取原始 ffprobe、远程 ff、本地缓存、SHA1、播放直链、Pickcode、Cookie、模型密钥、数据库或全局日志。

## 生命周期

识别与整理分别排队；识别完成不等于整理完成。任务状态和安全错误为白名单 DTO。取消向支持上下文的宿主调用传播；停用后不允许新能力调用。升级不执行迁移脚本，兼容配置保留；回退后必须重新启用。重启不会自动重放可能已提交的整理。

独立进程是能力与故障边界，不等于完整 OS 沙箱。生产部署继续保留许可证、runtimeguard、加固和最小权限。详细额度见 [系统设计](../plugins-design.md)。
